## Behavior
Observable change is test-only: the ADR 0004 concurrency guarantees now have direct regressions for the driver combinations and fail-policy variants that previously had no coverage. No production behavior, API, contract, or status changes in this pass.

- Signal-vs-poller on one shared value produces one committed transition and one `CapabilityReady`; the loser does not publish.
- Recovery and a Run-loop completion handler each serialize with a concurrent signal on the shared execution's `RunTransition` guard; the signal cannot publish while either holds the guard.
- A failure-policy deadline that wins the shared execution leaves no `CapabilityReady` and no dispatch intent for the failed capability; when a sibling capability is resumed on the same failed execution, the only ready event and intent belong to the resumed capability, never the failed one.

All new tests use a `start`/gate barrier, buffered result channels, time-bounded selects, and assert only from the test goroutine (no `t.Fatalf` from a worker goroutine).

## Risks and limitations
- The recovery-vs-signal, Run-loop-vs-wait-driver, and two fail-policy variants force a deterministic interleaving with a committer gate; they prove the loser cannot publish while the winner holds the guard, but they do not enumerate every scheduling interleaving. The `-race -count=50` stress covers repetition.
- The two fail-policy variants gate the deadline-failure commit so the failure wins deterministically; they assert the bus events plus durable status/intents, and do not rely on `recordingWaitStore`'s on-entry "commit" log as an outcome signal. The distinct-capability variant resumes the sibling after the failure commits because `MarkFailed` leaves other capabilities waiting and `SaveWaitTransition` does not reject a terminal execution; the asserted invariant is that the ready event/intent belong only to the resumed capability and the failed capability produces no ready event/intent.
- ADR 0004 open question remains open and is not fixed here: `RecoverableDispatch` re-dispatches an already-`CapabilityReady` capability, so a recovery invoked *after* a live signal resolved the same capability could still publish a second `CapabilityReady`. Recovery is documented startup-only; this test deliberately uses a non-due signal wait (which recovery never resumes) to avoid asserting behavior the ADR explicitly excludes from T-041.
- `go test -run 'Concurrent|Signal|Timer|Recover|RunLoop|Guard'` also selects `TestConcurrentClaimDispatchIntentWinnerLoserAndRecovery` (T-042). The 50-count run passed; the dispatch-claim flake was fixed in 29c3ab0 per the ledger. The separate stopped-capability flake (T-042) is uncharacterized and unrelated.
- PostgreSQL parity remains unverified (no `NEURON_TEST_POSTGRES_DSN`); these tests use the in-memory store only.
