# Security review — FINAL-SIGNOFF-SEC-CLI

status: approved
scope: commit aa4b497; `application/internal/cli/bootstrap/runtime.go`, `application/internal/cli/instance/*`, `application/internal/cli/run/run.go`; trust boundaries to `shared/types/projectruntime`, `shared/types/apitoken`, `application/connection`, `application/internal/cli/bootstrap/client.go`, `nore/cmd/nore/main.go`, and `nore/internal/api/middleware`.
threat model: assets = project-runtime bearer token, instance/execution authority (list, signal, cancel, remove, run), local project filesystem, HTTP endpoint selection. Entry points = discovery JSON under `<projectRoot>/.neuron/runtime/`, `--remote`/`daemon.endpoint` config, `--port`, `NEURON_API_TOKEN`, CLI commands. Boundaries = CLI process vs project-runtime process over loopback HTTP; local daemon socket vs explicit remote HTTP. Attacker capabilities = local write access to discovery metadata, control of a reachable HTTP endpoint, or a malicious discovery record; no remote unauthenticated caller is introduced by this change. Impact = credential disclosure, unauthorized instance mutation, or command redirection only under the local-write precondition described below.

## Findings

### [medium] Discovery records remain unauthenticated filesystem metadata (pre-existing; not introduced by T-082)
- file:line: `application/internal/cli/bootstrap/runtime.go:118-155`; `shared/types/projectruntime/projectruntime.go:44-48,130-162,194-223`; `nore/cmd/nore/main.go:565-610`.
- attack path or failure: A process able to write a JSON file under `<projectRoot>/.neuron/runtime/` (or under an ancestor checked by the upward walk) can publish an attacker-controlled `Host`, `Port`, `ProjectRoot`, live `PID`, and `Token`. `findRuntimeRecord` walks up and `selectRuntimeRecord` accepts the first record whose PID is alive and whose `ProjectRoot` string matches; `DiscoverProjectRuntime` then returns `record.Endpoint()` and `record.Token`, and `SetupInstanceClient`/`NewProjectRuntimeClient` send instance commands and the bearer token to that endpoint over plain HTTP. Nothing ties the endpoint or token to the recorded PID.
- impact: redirection of CLI authority (`signal`, `cancel`, `remove`, `clear`, `list`, `run`) and presentation of the recorded bearer credential to an attacker endpoint. The API authenticates on that token, so a redirected CLI authenticates to the attacker server.
- preconditions: local write access to the project (or an ancestor) state directory and a live PID in the forged record. Records written by the runtime are `0700` directories and `0600` files (`projectruntime.go:44-48,141-146`), so cross-user forgery is blocked; a same-user attacker can already read the `0600` token and call the real API directly, so this adds little privilege.
- evidence: `runtime.go:161-169` validates only PID liveness and root-string equality; `record.Endpoint()` is plain HTTP (`projectruntime.go:112-120`); the project runtime generates a real token and writes the record at `nore/cmd/nore/main.go:565-568,607-610`. The identical discovery logic was removed from `run/run.go` and moved into bootstrap by this commit, so `neuron run` already carried this trust property before T-082; the change extends it to instance commands rather than creating it.
- remediation: not required for T-082 acceptance. Longer term, bind discovery to process identity or a protected IPC channel (for example, peer-credential socket or endpoint/PID attestation) instead of trusting mutable JSON, and ensure ancestors cannot supply records for descendant projects.
- blocks acceptance: no

No critical or high findings were identified in the commit under review.

## Controls verified
- Token handling: `NewProjectRuntimeClient` (`runtime.go:81-89`) applies the discovery token only via `HTTPTransport.WithToken`; `HTTPTransport.authorize` places it in the `Authorization` header, never the URL (`application/connection/connection.go:102-109,290-293`). Discovery errors wrap only validation failures and do not include the token (`runtime.go:66-73`, `runtime.go:160-169`); `TestSetupInstanceClientStaleRecordDoesNotLeakToken` (`runtime_test.go:300-307`) asserts this.
- Explicit remote preserved: `SetupInstanceClient` delegates any configured `cfg.Daemon.Endpoint` to `SetupClient` (`runtime.go:99-103`); `--remote` populates `daemon.endpoint` (`application/internal/cli/cli.go:117-118`); `SetupClient` uses `connection.NewRemote` (`bootstrap/client.go:39-48`), which still honors `NEURON_API_TOKEN` (`application/connection/remote.go:18-24`). `TestSetupInstanceClientHonorsExplicitEndpoint` (`runtime_test.go:262-298`) proves a decoy discovery record is ignored when an explicit endpoint is set.
- Shared implementation: all instance commands route through the same `setup` helper (`instance/list.go:72,105`, `instance/signal.go:52`, `instance/cancel.go:36`, `instance/remove.go:33,51-56`, `instance/clear.go:22`), and `run.go:117-127` uses the same `DiscoverProjectRuntime`/`NewProjectRuntimeClient` helpers. No duplicated token/discovery logic remains.
- No new secrets or dependencies: the commit adds no dependencies, manifest changes, or real credentials; test tokens are obvious fixtures (`runtime_test.go:48,81,99,115-116,151,180,239,275,300`). No public API or protocol files are touched (`git show --name-only aa4b497`).
- Server-side authority: project runtime generates a random 32-byte token (`shared/types/apitoken/token.go:62-69`; `nore/cmd/nore/main.go:565-568`) and installs token auth on all non-health routes (`nore/cmd/nore/main.go:640`; `nore/internal/api/routes/routes.go:31,78`; `nore/internal/api/middleware/auth.go:34-65`), so the header is meaningful.
- Focused verification: `git diff --check aa4b497^ aa4b497` clean; `cd application && GOWORK=off go test -count=1 ./internal/cli/bootstrap ./internal/cli/instance ./internal/cli/run` all PASS (bootstrap 0.301s, instance 0.032s, run 15.169s).

## Unverified areas
- Ledger acceptance item "acceptance tests prove list/signal reach the runtime that owns a recovered execution after restart" was not executed in this security review; T-082 evidence records that final acceptance verification is deferred to the end of Phase 5 (`.agents/ledger.yaml:1604-1606`). This is functional acceptance owned by reviewer/coordinator, not a security blocker.
- `isProcessAlive` uses `syscall.Signal(0)` (`runtime.go:173-180`); Windows behavior was not verified and may mark all records stale. That is an availability/portability concern, not a confidentiality or integrity issue.
- The full race suite and `scripts/script.sh` were not run by this review; only the focused CLI packages and diff hygiene were verified here.
- The `--port` override branch adopts a discovery token without validating that the record's host matches `cfg.Runtime.Host` (`runtime.go:53-63`). This logic predates T-082 and instance commands never call it with a non-empty override, so it was not treated as a new finding.

## Residual risk
- Unauthenticated discovery metadata is inherent to the existing project-runtime design; it is mitigated by owner-only record permissions, generated high-entropy tokens, and the fact that same-user attackers already possess equivalent local authority. Accepted as pre-existing by the architecture that introduced `shared/types/projectruntime`; T-082 does not worsen it beyond adding more commands to the same trust path.

## Verdict
APPROVE. Commit aa4b497 centralizes discovery and token adoption without leaking the token into errors or logs, preserves explicit `--remote`/socket workflows, and routes all instance commands through the shared project-runtime client. The one medium observation is a pre-existing filesystem-discovery trust property, not a regression introduced by this task; it does not block T-082 security acceptance.
