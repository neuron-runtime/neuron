## Root cause
- `nore/internal/execution/dispatch_intent_test.go:227` — the concurrent-claim test deliberately uses a **5ms** lease. The winner stores `LeaseExpiresAt = now + 5ms`; under `-race` scheduling/CPU contention the loser's `claimDispatchIntent` transaction can read the record only after that window has elapsed, so `dispatchIntentClaimable` (`nore/internal/execution/store.go:699-707`) treats the winner's claim as expired, the loser's compare-and-swap succeeds against the unchanged value, and both goroutines report `won == true`, failing the assertion at `dispatch_intent_test.go:262`. The CAS/lease production mechanism itself is sound: the sibling test `TestConcurrentClaimDispatchIntentHasOneWinner` (`dispatch_intent_test.go:391`) uses a `time.Minute` lease and does not flake. This is a test-timing defect, not a scheduler defect.
- `TestStoppedCapabilityPublishesCancellationNotFailure` — **root cause not established**. It did not reproduce in ~500 focused/suite race runs. The reviewer's exact 5s failure text is not recorded in `AGENTS` reports, the ledger, the decisions, or `todos/TODO.md:821`; the brief only paraphrases it as "timed out after 5s". No source change was made without a reproduction.
