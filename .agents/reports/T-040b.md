Builds a durable `StatusWaiting` execution through the real execution mutators (`EnterWait` / `BeginRetryWait`), snapshots and reloads it without a blueprint, persists it, loads it back from the store, and calls `Instance.RecoverExecution` with the instance's recompiled blueprint. No production code changed; no wait or recovery logic duplicated in instance.

## Behavior
- A non-due signal wait stays `CapabilityWaiting` / `StatusWaiting`, keeps `InFlight()==0`, and produces zero `CapabilityReady` events, zero `ExecutionFailed` events, and zero dispatch intents at the instance boundary; the durable snapshot also stays waiting.
- An elapsed timer wait and an elapsed retry wait each resume exactly once: one `CapabilityReady` event for `cap`, one ready dispatch intent in durable storage, wait metadata cleared, `StatusRunning`, `CapabilityReady`, `InFlight()==1`, and the durable snapshot is running.
- The test asserts the instance attached its recompiled blueprint, proving the recovery path ran through `Instance.RecoverExecution` -> `Scheduler.RecoverExecution` rather than a test-local imitation.

## Risks and limitations
- The instance in the new tests is intentionally not started, so the CapabilityReady event and ready dispatch intent stay observable instead of being consumed by the engine. This tests the recovery commit/publish boundary, not engine claim-and-run; engine-side execution is covered by execution/engine tests.
- The fixture uses the in-memory SQLite store (the package's `newTestStore`). No PostgreSQL claim is made or implied.
- `Instance.Stop()` in cleanup sweeps the still-waiting non-due execution to failed; this happens after all assertions and mirrors the documented stop semantics. No test relies on the post-cleanup state.
- Concurrent recovery (T-041) is a known open risk in the ledger; these tests exercise one recovery call per execution and do not attempt concurrent signal/timer/recovery drivers.
