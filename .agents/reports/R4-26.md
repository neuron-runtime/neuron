## Root cause
- nore/internal/instance/manager.go:189-211 — The `recoveryKey` function builds a resolution key from the instance's persisted metadata (AssemblyID, Version, Hash, Env). When an execution is recovered after a runtime crash, this key is used with `assemblies.Resolve()`, which with a hash supplied calls `resolveByHash()` — an exact match that never falls back to the version index's latest entry. The root cause was that no test existed to verify this pinning behavior against registered version bumps.

## Fix
- nore/internal/instance/recovery_test.go:241-289 — Added `TestRecoveryResumesAgainstOriginalArtifact` which:
  1. Registers assembly at v1.0.0 with hash "hash_v1"
  2. Starts a durable execution on v1.0.0
  3. Registers a NEW version 2.0.0 with different hash "hash_v2" (same assembly ID)
  4. Stops the manager (simulating runtime crash/termination)
  5. The manager reconciles and recovers the execution using `recoveryKey`, which prefers the metadata's hash "hash_v1"
  6. `assemblies.Resolve` with the hash resolves via `resolveByHash` to the exact original artifact, not the newer v2.0.0
  7. Verifies the execution completed successfully, proving artifact pinning works
